## Answer: no single vocabulary works — and entire.io already pays for pretending otherwise

**No harness has all four concepts.** Only Claude Code has three of them (skill/command/agent) as genuinely distinct on-disk kinds. Codex has two (skill, agent). Gemini has one verified (agent). Cursor, OpenCode, Copilot CLI, and Factory Droid have **zero** — they expose only hooks and a plugin/extension entry point. Your CLI cannot install "a skill" into Cursor at all; there's nowhere to put it.

**Same word, different things:**

- **"agent"** is the worst offender. In Claude Code, `.claude/agents/*.md` is a *subagent* (delegated Task-tool worker: has `model`, `color`, `tools`). In Codex, `.codex/agents/*.toml` is where entire puts its **skill** — the agent-help asset that in Claude Code lives in `skills/`. So a Codex "agent" is sometimes a subagent, sometimes a skill. Worse, entire's own registry uses "agent" to mean *the harness itself* (`AgentNameClaudeCode`, `AgentNameCursor` in `agent/registry.go:157-164`) — three meanings for one word in one codebase.
- **"skill"** in entire means both "a Claude Code skill" and "a Claude Code subagent" (the search skill) and "a Claude Code slash command" — the review picker at `review/picker.go:1211-1215` has one bucket labeled "Built-in commands" and another "Installed plugin skills", both feeding the same `Skills []string` field.
- **"plugin"** means a Claude/Codex marketplace bundle *containing* skills/commands/agents, but in OpenCode it means a single TypeScript hook file. Pi calls that same thing an "extension"; Gemini's install hint says `gemini extensions install`.

**Different words, same thing:** OpenCode "plugin" = Pi "extension" = Gemini "extension" = the hook-integration entry point. And Claude "command" / Codex "skill" / Pi "skill" are all just *the token a user types to trigger a canned prompt* — differing only in sigil, which entire abstracts into `InvocationForm` (`skilldiscovery/scan.go:24-42`, `SlashForm` vs `DollarForm`).

**The leak to avoid:** `settings/settings.go` documents `ReviewConfig.Skills` as "the list of **slash-prefixed** skill invocations", but Codex discovery emits `$`-prefixed names, and `registry.go:72-76` contains a bug-comment explaining that a slash-form entry in Codex's suppression list "could never intersect the discovered set, so the hint would show forever." That is exactly the class of bug you get from adopting one harness's vocabulary as your neutral one.

**Recommendation:** define your own neutral types, and make the harness adapter own both the name and the *availability*. A workable minimal set, grounded in what actually varies here:

1. `instruction` (always-on context) — target: `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` / Gemini's configurable `context.fileName`.
2. `capability` (model-triggered, description-matched, progressive-disclosure) — Claude `skills/`, Codex `skills/`, Pi `/skill:`.
3. `command` (user-triggered by an explicit token) — Claude `commands/`, with a per-harness sigil (`/` vs `$`), unavailable on Codex-under-exec.
4. `persona` (delegated worker with its own tool/model budget) — Claude `agents/`, Codex `agents/*.toml`, Gemini `agents/*.md`.

Then make "unsupported" a first-class outcome rather than an error — the CLI already does this well with `managedScaffoldUnsupported` (`setup_agent_help_skill.go:75-77`), which prints "Agent-help skill is not supported for %s" for the four harnesses that have nowhere to put one. ### The `hooks/` caveat — important

`.claude/hooks/` is **not** a config-discovery directory. The only binary references to `join(".claude","hooks")` are in the **sandbox/permission path registration** walk — i.e. it pre-authorizes reading and executing files there. It is a conventional place to *park hook scripts*.

Hook *configuration* lives in exactly two places:
- `settings.json` / `settings.local.json` under the `"hooks"` key (this is what both your user and harnaas project settings do), or
- a **plugin's** `hooks/hooks.json` (the `"hooks","hooks.json"` join exists only on the plugin loading path).

So a CLI that drops a `hooks.json` into `.claude/hooks/` and expects it to load **will silently do nothing**. It must edit `settings.json`.

**Rules** (`.md`) — **no required frontmatter at all**. A bare markdown file works. One optional key controls scoping, `paths`:

```js
function ud_(e){
  let {frontmatter:t, content:r} = sf(e);
  if(!t.paths) return {content:r};
  let n = qSo(t.paths).map((o)=&gt; o.endsWith("/**") ? o.slice(0,-3) : o)
                      .filter((o)=&gt; o.length&gt;0);
  if(n.length===0 || n.every((o)=&gt;o==="**")) return {content:r};
  return {content:r, paths:n};
}
```

The parsed `paths` becomes the internal `globs` field, and the loader partitions on it:

```js
f.push(...x.filter((k) =&gt; o ? k.globs : !k.globs));   // o === conditionalRule
```

Because the four scope calls above all pass `conditionalRule: false`, **the always-loaded pass takes only rules WITHOUT `paths`**. Rules **with** `paths` are held back and injected later when you touch a matching file (load reason `path_glob_match`, matched with the `ignore` package against the repo-relative path). `paths: ["**"]` is treated as unscoped.

Practical upshot for your CLI: **omit `paths` for always-on rules; add `paths` for file-type-scoped rules.** Both are legitimate; they just load at different times.

## 2. Plugin system

### `~/.claude/plugins/` layout (verified)

```
~/.claude/plugins/
├── installed_plugins.json      # what is installed, where, which version
├── known_marketplaces.json     # marketplace name → source + installLocation
├── plugin-catalog-cache.json   # 406 KB catalog cache

├── cache/&lt;marketplace&gt;/&lt;plugin&gt;/&lt;version&gt;/    # ← versioned plugin payloads
└── data/&lt;plugin&gt;-&lt;marketplace&gt;/               # plugin runtime state
```

**Versioning/caching is the key architectural fact:** plugin payloads live at `cache/&lt;marketplace&gt;/&lt;plugin&gt;/&lt;version&gt;/`, e.g. `cache/claude-plugins-official/mattpocock-skills/1.2.3/`. Multiple versions coexist side by side. `installed_plugins.json` maps id → `{scope, installPath, version, installedAt, lastUpdated, gitCommitSha}`, and the value is an **array**, so one plugin can be installed at several scopes at once. `scope` is `"user"` or `"project"`; project-scoped entries carry a `projectPath`.

Liveness is tracked by an `.in_use/` marker directory inside each cached version (present in the two currently-enabled plugins, `figma/2.2.91` and `mattpocock-skills/1.2.3`), swept per `.last_inuse_sweep`.

Enablement is **not** in `installed_plugins.json` — it is in `settings.json` under `enabledPlugins`, keyed `plugin@marketplace` → bool. Your user settings currently have `figma` and `mattpocock-skills` true; `superpowers`, `ecc`, `supabase` false. Marketplaces can also be declared in settings via `extraKnownMarketplaces`.

## Recommendation

Install **raw files**, not a plugin, for rules. Rules have no plugin equivalent — `plugin.json` has no `rules` key and no plugin in the official marketplace ships one. `.claude/rules/*.md` is the only route, it is auto-loaded, it needs no manifest, and it is trivially uninstallable.

Concretely:
- Write rule files to `.claude/rules/&lt;your-cli&gt;-&lt;topic&gt;.md`. Namespace the filenames so uninstall is a glob and you never collide with a user's own rules.
- **Do not touch `CLAUDE.md`.**
- Use `paths:` frontmatter only for genuinely file-scoped rules; omit it for always-on guidance.
- If you also ship commands/agents/skills, reconsider: those *do* have a plugin equivalent, and the plugin route gives you versioning, `enabledPlugins` toggling, clean uninstall, and updates. A checked-in `directory`-source marketplace at `.claude/plugins/` (the `entire-dev-tools` pattern, minus its two path bugs) is the lowest-friction version of that.
